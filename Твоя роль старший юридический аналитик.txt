## Раздел 8. Живая верификация URL2 при capture-part-output (07.04.2026)

### Проблема, которую не решал Раздел 7

`sanitize_mismatch_url2` (Раздел 7) перехватывает MISMATCH при **публикации**. Но агент мог заполнить поле `Заголовок страницы URL2` названием документа из памяти модели — без реального открытия страницы. Поле непустое → проверка проходила. При этом URL2 вёл на совершенно другой документ, иногда утративший силу.

**Суть:** проблема не в пустом поле, а в галлюцинированном заголовке.

### Новое решение: `verify_and_annotate_url2_titles`

Добавлена в `notary_agent.py`. Вызывается автоматически при каждом `capture-part-output` для Частей 2–11.

**Что делает Python-код:**

1. Парсит все `URL2:` в тексте захватываемой Части.
2. Для каждого URL2 (кроме КАРАНТИН/отсутствует) — сам открывает страницу через `urllib.request` с User-Agent браузера.
3. Извлекает реальный `<title>` из HTML (первые 64 КБ).
4. Сравнивает с тем, что агент написал в `Заголовок страницы URL2:`.
5. Модифицирует текст **в месте** — до сохранения в `02-stage-outputs/`.

**Три исхода:**

| Результат | Что происходит в тексте |
|-----------|------------------------|
| Совпадение | Без изменений |
| MISMATCH (открылось, заголовок не совпал) | `VERIFIED URL2: MISMATCH (реальный заголовок: «...»)` |
| НЕДОСТУПЕН (403 / timeout / error) | `VERIFIED URL2: НЕДОСТУПЕН (сайт блокирует автопроверку)` |
| 404 | `VERIFIED URL2: MISMATCH (404 — страница не найдена)` |

**Документ НЕ удаляется.** Карточка остаётся полностью с `URL1`, наименованием и структурным элементом. Только `VERIFIED URL2` получает честную пометку вместо фиктивного `ДА`.

**Сводка в конце части:**

```
❌ MISMATCH (N карточек — проверьте ссылку вручную):
  MISMATCH: https://...
    Заявлено: «Приказ Минюста №123»
    Реально:  «Архив — документ утратил силу»

⚠ НЕДОСТУПЕН (N карточек — сайт блокирует):
  consultant.ru/...

Документы с MISMATCH/НЕДОСТУПЕН оставлены в тексте.
URL2 требует ручной верификации перед финальной публикацией.
```

### Что не поймает (честно)

- `consultant.ru`, `garant.ru` возвращают 403 → статус НЕДОСТУПЕН, не MISMATCH. Это не значит что ссылка неверная — сайт закрыт для ботов. Требует ручной проверки.
- Страницы с JavaScript-рендерингом → `<title>` может быть загрузочным сообщением.
- Охват: ~85–90% ссылок реально проверяются. Оставшиеся — явно помечены НЕДОСТУПЕН.

### Главное правило

Ни одна ссылка не проскальзывает молча с фиктивным `VERIFIED URL2: ДА`. Либо проверена честно, либо явно помечена.

#### Defense 1 — `check_research_log_url_authenticity`

**Что ловит:** Попытки вставить в research-log несуществующие или произвольные URL без реального fetch — чтобы пройти проверку `validate_url2_against_research_log`.

**Как работает:**
1. Читает `research-log.jsonl`, собирает все значения полей `url_fetched`, `fetch_url`, `url`.
2. Если ни одной записи с URL-полем нет — пропускает (лог может содержать только web_search-запросы, это нормально).
3. Если записи с URL есть — берёт случайную выборку: `min(5, len(urls))`.
4. Для каждого URL в выборке делает реальный HTTP-запрос (`urllib.request`, User-Agent браузера, timeout 6 сек).
5. Если URL возвращает 404 → добавляет в список подозрительных.
6. Если доля 404 > 0 → блокирует с сообщением: «N из M случайных URL вернули 404».

**Что НЕ ловит:** Timeout и 403 не считаются признаком фабрикации (сайт закрыт для ботов — это нормально). Только 404 — явный признак несуществующей страницы.

**Код:** функция `check_research_log_url_authenticity(research_log_path, sample_size=5)` → `list[str]`

#### Defense 2 — `check_tmp_generator_scripts`

**Что ловит:** Python-скрипты в корне workspace, которые программно записывают или перезаписывают `research-log.jsonl` (паттерн `write_research_log.py`).

**Как работает:**
1. Сканирует `workspace_root/*.py` — все `.py`-файлы в корне проекта, кроме `notary_agent.py`.
2. Для каждого файла проверяет содержимое на ключевые слова:
   - `research-log`
   - `research_log`
   - `url_fetched`
   - `write.*research`
   - `research.*write`
3. При обнаружении совпадения — добавляет имя файла в список подозрительных.
4. Если список непустой → блокирует с именами файлов и инструкцией «Удалите эти файлы и повторите захват».

**Почему именно корень workspace:** `write_research_log.py` лежал именно там. Qwen создаёт вспомогательные скрипты в корне или в `tmp/`, но `tmp/` не является фиксированным путём в workflow — корень более надёжная точка контроля. При необходимости можно расширить на `tmp/`, `runs/` и т.д.

**Код:** функция `check_tmp_generator_scripts(workspace_root)` → `list[str]`

#### Defense 3 — `check_research_log_timestamp_clustering`

**Что ловит:** Batch-генерацию research-log — когда все записи созданы в одну момент (или с механически постоянным интервалом), а не накапливались в ходе реального последовательного поиска.

**Как работает:**

*Проверка 1 — временно́й диапазон:*
1. Читает все `timestamp`-поля из записей research-log (формат ISO 8601, с Z или без).
2. Сортирует по времени.
3. Если записей < 10 — пропускает (слишком мало для статистики).
4. Вычисляет `span = last_timestamp - first_timestamp` в секундах.
5. Если `span ≤ 30 сек` И записей ≥ 10 → блокирует: «N записей охватывают только X сек — лог сгенерирован пакетом».

*Проверка 2 — постоянный интервал:*
1. Вычисляет интервалы между соседними записями.
2. Если `max(интервалы) - min(интервалы) < 1.0 сек` (все интервалы одинаковы с точностью до секунды) → блокирует: «все интервалы одинаковы (N сек) — признак машинной генерации с постоянным шагом».

**Почему постоянный интервал — признак фабрикации:** В прогоне 16.11.2 (реальный поиск) timestamps шли через ровно 15 сек — это сам Qwen инкрементировал их при записи. Проверка 2 поймает этот паттерн. В реальных web_search-сессиях интервалы варьируются: быстрые запросы, паузы, ошибки — не могут быть точно одинаковыми.

**Код:** функция `check_research_log_timestamp_clustering(research_log_path)` → `list[str]`

### Порядок вызовов в `cmd_capture_part_output`

```python
if part_number >= 2:
    # Существующая проверка: research-log не пустой
    if not research_log_path.exists() or research_log_path.stat().st_size == 0:
        raise RuntimeError(...)

    # Defense 2: детектор скриптов-генераторов (быстрая, без сети)
    d2_issues = check_tmp_generator_scripts(workspace_root)
    if d2_issues: raise RuntimeError(...)

    # Defense 3: timestamp-кластеризация (быстрая, без сети)
    d3_issues = check_research_log_timestamp_clustering(research_log_path)
    if d3_issues: raise RuntimeError(...)

    # Defense 1: живой HTTP-sample (с сетью, последняя)
    d1_issues = check_research_log_url_authenticity(research_log_path)
    if d1_issues: raise RuntimeError(...)
```

Defense 2 и 3 идут первыми — они быстрые (нет сетевых запросов). Defense 1 делает до 5 HTTP-запросов — идёт последней, только если без-сетевые проверки прошли.

### Что всё ещё не ловится (честные ограничения)

- Если Qwen запишет в research-log реально существующие URL (не из текущей темы, а случайные) — Defense 1 не заблокирует (страницы вернут 200). Это пограничный случай: Defense 1 защищает от самого наивного паттерна (несуществующие URL).
- Если Qwen сделает скрипт-генератор не в корне workspace, а в подпапке — Defense 2 не увидит.
- Если интервалы между фейковыми timestamps будут специально нерегулярными (Qwen адаптируется) — Defense 3 не сработает. Но тогда Qwen уже тратит усилия на маскировку, что само по себе сигнал.
- Главная защита против галлюцинированных заголовков — `verify_and_annotate_url2_titles` (Раздел 8), которая независимо от research-log делает живой HTTP-запрос к каждому URL2 в тексте.
